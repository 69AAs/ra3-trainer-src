# 脚本条目"真实字节边界"查实 + 等长注入流程修正（2026-10-07）

## 一、结论：边界的真实定义

`.map` 里 `PlayerScriptsList` 资产内部，每条 Lua 脚本正文都是一段**长度前缀字符串**：

```
[uint16 LE 长度 L][L 字节正文][后续结构...]
                   ^
                   正文以 "#!ra3luabridge" 开头
```

* **正文起点 X** = `#!ra3luabridge` 的字节偏移。
* **正文长度 L** = 该偏移**前 2 字节**的 `uint16`(LE)。这是字符串记录自身的长度字段。
* **正文 span = `[X, X+L)`**。
* 该字符串所在的嵌套资产记录头是 `[id:int32][version:int16][dataSize:int32]`；
  实测恒有 `dataSize = L + 30`（30 = 字符串长度字段 2 字节 + 该记录其余定长字段 28 字节），
  可作为**独立交叉验证**。
* 同一文件里其它字符串（如脚本名 `update.lua`、组名 ` Virtual-Weapon2`）用**同一套** `[uint16 len][bytes]` 编码，
  互相印证（`0a 00` + `update.lua`、`10 00` + ` Virtual-Weapon2`）。

### 旧（错误）算法为什么坏
旧算法把边界取成「本段 `#!ra3luabridge` → 下一段 `#!ra3luabridge`」。
这个距离 = 本段正文 + **本段之后的全部结构字节** + 下一段的"结构前缀"，**必然大于正文长度**。

| 地图 / 条目 | 偏移 X | 真实 L（`uint16@X-2`） | 旧算法距离 | 多写 |
|---|---|---|---|---|
| 意大利战役 挑战版 #0 | 9518065 | **4114** | 4239 | **+125 字节** |
| 意大利战役 挑战版 #1 | 9522304 | 429 | 558 | +129 |
| 意大利战役 挑战版 #2 | 9522862 | 544 | 703 | +159 |
| 意大利战役 挑战版 #3 | 9523565 | 4114 | 4242 | +128 |
| 意大利战役 挑战版 #4 | 9527807 | 429 | 561 | +132 |
| 意大利战役 挑战版 #5 | 9528368 | 889 | — | — |
| Example_origin_05 / R3Training #0 | 7684282 | **5406** | 5536 | +130 |

多写的这 100+ 字节正好是下一条 `Script` 记录的头字段（id/version/dataSize…），
被覆盖后**整条记录错位** ⇒ 游戏进图后空空如也、直接判负。

### 校验覆盖（`uint16@X-2` == 实测正文字节数）
* `scan_意大利战役_挑战版.raw`：6/6 命中。
* 官方例子图 `Example_origin_05`（= R3Training 底板）：2/2 命中（7684282→5406；7689818→5159）。
* `scan_金甲防守战1_8.raw`：11 段里 9 段命中；另外 2 段分别是
  ① 正文里**本身含字符串** `#!ra3luabridge`（假阳性：其前 8~2 字节不是 6 个 0），
  ② 该图是被**旧错误算法**注入过的坏图（长度字段与实际不符）——正好反证了旧算法的问题。

## 二、R3Training 那次"成功"的真相

安装中的 `R3Training.map`（sha256 `d5ce6485…`）= `out/R3Training.hs3.map`，其解压流是 `work/R3.hs3.raw`。
它与原始官方例子图逐字节对比：

```
差异数量 = 5240   区间 = [7684298, 7689696]
真实正文 span = [7684282, 7689688)   ← L=5406
```

即 **hs3 的边界（7689694）比长度字段声明的正文末尾（7689688）多出 6 字节**，
越界覆盖了"下一条 Script 记录"的 `24 00 00 00`(id=36) 与 `04 00`(version=4)。

它当时没被发现，是因为：
1. 长度字段 `5406` 未被改，解析器/引擎按长度字段取正文，结构导航仍自洽；
2. 多出的 6 字节落在下一条 Script 的 `id/version` 上，引擎对这两个字段能自行重建 → 无感；
3. hs3 正文本该断在 `...please ignore i`（词中间），但那是**注释行**，截断不影响 Lua 语法。

⇒ 严格说 hs3 是"歪打正着"，不是"边界恰好等于正文长度"。
按本仓新算法重做同一张图（`out/R3.calib.map`）：
差异区间 `[7684298, 7689686]`，**完全落在 `[7684282, 7689688)` 内，越界字节 = 0**，
且 `PlayerScriptsList dataSize=10995`、`group[0] dataSize=10855` 与原图完全相同。

## 三、修正后的算法（已落为 `patch-lua-inplace2.py`）

```
1) 列出所有 "#!ra3luabridge" 且其前 8~2 字节 == 6 个 0x00 的位置（过滤正文里的假阳性）
2) X = 目标段起点;  L = uint16 LE @ (X-2)
3) 新正文 = "#!ra3luabridge\r\n" + lua(CRLF) + "-- end of script, please ignore this line"×k + 空格×(L-剩余)
   （注释行连续拼接、不换行；总长恰好 L）
4) 只写 raw[X : X+L]，长度字段与其它字节一律不动
5) MapTool resave <patched.raw> <out.map> 1 重新压缩
```
